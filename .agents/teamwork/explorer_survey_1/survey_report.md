## 1. Backend Architecture & Server Entrypoints

### 1.1 Process Lifecycle & Supervision Chain

```
[start_forever.bat / start_btc_server.vbs]
               │
               ▼
      server_watchdog.py  (Supervises launch_desktop.py + ngrok daemon)
               │
               ▼
      launch_desktop.py --no-browser
         ├── Thread: WorkerSupervisor ──► subprocess.Popen([python, "backend/worker.py"])
         └── subprocess.run([python, "-m", "uvicorn", "backend.main:app", ...])
```

1. **`server_watchdog.py`**:
   - Acquires a Windows named kernel mutex: `"KalshiAITraderWatchdogLock"` (`server_watchdog.py:120`).
   - Starts a background daemon thread `NgrokMonitor` (`server_watchdog.py:112`) that ensures `ngrok http 8058 --url=moneyprinter.ngrok.app` is running.
   - Runs `launch_desktop.py --no-browser` in a subprocess, reads lines from `stdout`, logs them to `server_watchdog.log`, and restarts the server on unexpected termination with exponential backoff (`server_watchdog.py:164`).
2. **`launch_desktop.py`**:
   - Checks if port 8058 is already responding via `HEALTH_URL = http://127.0.0.1:8058/api/health` (`launch_desktop.py:24-46`).
   - Spawns a background thread `WorkerSupervisor` (`launch_desktop.py:100-114`) that executes `backend/worker.py` and restarts it with backoff if it exits.
   - Spawns `uvicorn backend.main:app --host 0.0.0.0 --port 8058 --no-access-log` (`launch_desktop.py:83-87`).
3. **`backend/worker.py`**:
   - Single-instance background process guarded by `CrossProcessLock("worker_singleton", timeout=0)` (`backend/worker.py:28-33`).
   - Spawns thread `FastExitWatcher` (`backend/worker.py:50-58`) which invokes `fast_exit_check()` every 1.5 seconds.
   - Initializes Forex auto executor (`backend/worker.py:40`).
   - Runs a continuous `while True` loop (`backend/worker.py:61-90`) evaluating BTC, ETH, and GOLD via `AutoExecutor`, settling trades via `settle_saas_trades()`, and archiving old trades every 60 iterations. Sleep delay between cycles is only **1.0 second**.
4. **`backend/main.py`**:
   - FastAPI server mounting CORS, `SecurityMiddleware` (rate limits non-polling API calls to 5,000 req/min), `GuestMiddleware`, CSRF prevention middleware (`block_cross_site_writes`), and legacy JWT refresh middleware (`refresh_legacy_session_token`).
   - `lifespan` handler (`backend/main.py:86-104`) initializes socket exception handling on Windows, liquidation WebSocket feed, and self-heals expired open trades via `reconcile_expired_open_trades()`.

### 1.2 Modular API Router Hierarchy

All endpoints are cleanly factored into specialized routers:

- `backend/routes/sports.py`: MLB pitcher strikeouts and international sports predictive models.

## 2. Kalshi Integrations & Rate Limiting (429 Vulnerabilities)

### 2.1 The Two Kalshi Clients

| Module | Purpose | Authentication | Rate-Limit / Retry Behavior |
|---|---|---|---|
| `backend/btc/kalshi_client.py` | Public market quote discovery (`get_kalshi_15m_market`), recent trades (`get_recent_trades`) | None (Public REST) | Uses `_safe_get` decorated with `@retry` on HTTP 429/502/503/504 (`kalshi_client.py:31`). Exponential backoff (1s - 10s, 4 attempts). In-memory caching with lock (TTL 0.95s). |
| `backend/btc/kalshi_trader.py` | Order placement, portfolio balance, positions, settlements | RSA-PSS SHA256 API Key | Direct `requests.Session`. **Missing or non-functional 429 retries across almost all methods.** |

---

### 2.2 Critical Vulnerability: Defective `@retry` on Kalshi Endpoints

In `backend/btc/kalshi_trader.py`, `get_market_result()` (line 442) and `get_market_quote()` (line 473) are decorated with tenacity `@retry`:

```python
# backend/btc/kalshi_trader.py:442-461
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=0.5, min=1, max=5),
       retry=retry_if_exception_type((requests.exceptions.RequestException, requests.exceptions.Timeout, requests.exceptions.ConnectionError)))
def get_market_result(self, ticker: str) -> Dict[str, Any]:
    ...
    resp = self.session.get(f"{BASE_URL}{path}", ...)
    if resp.status_code != 200:
        return {
            "success": False,
            "result": "",
            "error": f"HTTP {resp.status_code}: {resp.text}",
        }
```

#### Why This Fails:
1. `requests.Session.get()` does **not** raise an exception when receiving HTTP 429 (Too Many Requests). It returns a valid `Response` object with `status_code = 429`.
2. The code checks `if resp.status_code != 200` and immediately returns `{"success": False, "error": "HTTP 429..."}` without calling `resp.raise_for_status()`.
3. Because no exception is raised, tenacity's `@retry` **never triggers** on HTTP 429! The method returns an error payload on the very first attempt.

### 2.3 Critical Vulnerability: Runaway Settlement Polling (429 Storm Generator)

In `backend/saas_settler.py` (`_settle_saas_trades_pass()`, lines 734-750):

```python
# backend/saas_settler.py:734-750
if not market or market.get("status") != "active" or market.get("ticker") != ticker:
    from backend.btc.kalshi_trader import kalshi_trader
    res = kalshi_trader.get_market_result(ticker)
    ans = res.get("result", "").lower()

    if ans == "yes":
        exit_price = 1.0 if side.upper() == "YES" else 0.0
    elif ans == "no":
        exit_price = 1.0 if side.upper() == "NO" else 0.0
    else:
        # Only fallback to synthetic if it's explicitly a synthetic contract
        if "SYNTH" in ticker.upper() or "TEST" in ticker.upper():
            exit_price = ...
        else:
            continue # Wait for official Kalshi resolution
```

#### The Mechanism of Failure:
1. Kalshi 15-minute contracts often remain in "determining" or pending resolution status for 5 to 15 minutes after contract close before the official `result` is posted.
2. `backend/worker.py` runs a 1-second loop (`time.sleep(1)`). In addition, `fast_exit_check()` runs every 1.5 seconds.
3. For every open trade whose market has closed, `kalshi_trader.get_market_result(ticker)` is called **every single second**.
4. When `ans` is not `"yes"` or `"no"` (because Kalshi hasn't published the result yet, OR because Kalshi returned HTTP 429), it executes `continue`.
5. There is **no backoff**, **no per-ticker retry interval**, and **no negative caching**.
6. If 2 trades are waiting for settlement, the worker fires **120 Kalshi API requests per minute**. Kalshi's rate limit triggers HTTP 429.
7. As established in Section 2.2, `get_market_result()` returns `result: ""` on 429, triggering another request 1 second later, creating a self-sustaining 429 storm.

### 2.4 Lack of Rate Limit Protection on Account Operations

In `backend/btc/kalshi_trader.py`:
- `get_balance()` (`kalshi_trader.py:129-172`): Directly calls `self.session.get()`. If 429 occurs, returns `balance_dollars: 0.0` with no retry. In `saas_broadcaster.py:895-908`, this causes live trade execution to abort with `[SaaS Multitenant] User ... skipped LIVE: failed to fetch balance`.
- `get_positions()` (`kalshi_trader.py:740-753`): Directly calls `self.session.get()`. If 429 occurs, returns `positions: []` with no retry.
- `place_order()` (`kalshi_trader.py:997-1357`): Uses `self.order_session.post()`. If 429 occurs, returns `{"success": False, "error": "Kalshi Order Rejected (HTTP 429)..."}` with no backoff.

#### Why the Crash Occurs:

## 4. Worker Loops, Disk I/O & Log Flooding

### 4.1 The 48.6 Megabyte `watchdog_error.log`

- `watchdog_error.log` in the root directory grew to **48,655,782 bytes (~48.6 MB)**.
- Cause:
  1. `backend/worker.py` loop iterates with `time.sleep(1)`.
  2. For every iteration, it logs:
     `[Worker] Running loop for BTC`
     `[Worker] Running loop for ETH`
     `[Worker] Running loop for GOLD`
  3. Every 1.5 seconds, `fast_exit_check()` runs.
  4. In addition, `AutoExecutor` logs regime details and user evaluations every cycle.
  5. `server_watchdog.py:147-150` iterates over `proc.stdout` line by line, re-logging every line with `logger.info("[Server] %s", line_str)`.
  6. Writing dozens of log lines per second to unbuffered file handlers causes high disk I/O, potential pipe stalls on Windows, and massive log bloat.
